# 游戏工作目录与双平台协作约定

本页规定游戏分析工作目录的结构、双平台会话归档方式和临时文件命名，使 Codex 与 Claude 在同一台机器、同一批目录上协作时产出可互相接续。它不定义任何游戏的事件、属性或指标口径，那些只能来自 `knowledge/projects/<project>/`。

## 三层边界

体系分三层，各层职责不可混放。

云端 GitLab 仓库 `llm_wiki` 的 `main` 是唯一正式知识源。本地知识库仓库是它的副本，保存知识正文、共享 Skill 源文件和两个平台各自的运行配置源文件。游戏工作目录独立于仓库之外，不纳入 Git，存放具体分析过程与产物。

知识库仓库内部再分共享区与平台区。`knowledge/`、`.agents/skills/`、`inbox/`、`schemas/`、`scripts/` 由两个平台共建共用，同一份内容同时对 Codex 和 Claude 生效。`AGENTS.md` 与 `.codex/` 只服务 Codex，`CLAUDE.md` 与 `.claude/` 只服务 Claude；两侧内容应保持语义一致，差异仅限于各自的工具名、hook 协议和安装路径。修改任一侧的运行配置后，必须执行对应的安装脚本才会在全局生效，同步 hook 不会代劳。

游戏专属的业务知识、埋点定义、指标口径写进知识库 `knowledge/projects/<project>/`，随 Git 走审核流程；分析过程中产生的数据文件、图表、报告、会话记录留在游戏工作目录，不入库。判断标准是：能被下一次分析当作口径引用的进知识库，只是某一次分析的中间物或成果的留在工作目录。

## 游戏工作目录结构

每个游戏一个目录，与知识库仓库并列，目录名使用中文游戏名以便人工辨认（知识库内的项目目录名仍用小写拉丁标识，两者通过 `project.yaml` 对应）。

```text
<游戏名>\
├─ 目录说明.md          本目录用途与对应的知识库项目标识
├─ 专题·分析\           按专题组织的分析产物
├─ 参考资料\            埋点方案、历史文档等外部输入
├─ 知识学习\            设计产物与学习笔记
└─ 会话归档\
   ├─ Codex\<日期>\<任务名>\
   └─ Claude\<日期>\<任务名>\
```

两个平台共用前三个目录，读写同一批参考资料和分析产物，避免同一份埋点方案存两遍。只有 `会话归档/` 按平台分栏，因为会话上下文、中间脚本和产出格式与具体平台绑定，混在一起无法追溯是哪次会话产生的。

`会话归档/<平台>/<日期>/<任务名>/` 中，日期用 `YYYY-MM-DD`，任务名用能表意的短名。任务目录内建议再分 `work/`（脚本与中间件）和 `outputs/`（最终交付物），便于日后判断哪些可以清理。

跨平台接续同一件工作时，在任务目录内留一份交接说明，写明使用的口径来源、查询范围、已完成部分和待确认项，让另一个平台不必重读全部中间文件即可接手。

## 临时文件

分析过程中的临时脚本与中间数据统一使用 `.tmp_` 前缀，或集中放进任务目录的 `work/`。带前缀的文件视为可清理，不应被其他分析引用。

若某个中间产物构成了结论的证据（例如支撑留存结论的分组明细），应移出临时区、去掉前缀，放进 `outputs/` 并在交接说明中标注，否则清理时会连同证据一并丢失。

## 知识库仓库工作区整洁

两个平台的同步 hook 在启动时检查工作区状态，存在未跟踪文件时会执行 fetch 但不自动快进。因此仓库内不应长期堆积未跟踪文件：属于运行配置的纳入 Git，属于临时产物的写进 `.gitignore`，属于分析过程的移到游戏工作目录。

正式变更走分支加 Merge Request，两个平台都可以提交。涉及共享区的改动需要考虑对另一平台的影响，涉及平台区的改动应检查另一侧是否需要同步调整。
