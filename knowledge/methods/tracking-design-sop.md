# 埋点方案设计工作流

这是一套跨项目的动作顺序，不定义任何游戏的事件、属性或指标。

1. **读版本内容**：先读 PRD、更新内容、流程图和项目历史，列出玩家路径、状态变化、成功/失败/退出和边界。
2. **写分析问题**：把“要不要做这个埋点”改成上线后要回答的具体问题，并标出所需粒度和时间范围。
3. **查项目方案**：在当前数数方案、项目 Markdown 和历史验收记录中查事件、属性、显示名、类型、枚举和对象结构；项目未确认前不借用其他游戏。
4. **设计最小事件集**：同流程且属性相近时用一个事件加 `action_type`/`step`；生命周期、粒度或统计目的不同则拆开。
5. **补字段契约**：每行写触发时机、上报端、类型、必填/可空、枚举、单位、范围、对象行粒度和版本范围。
6. **做冲突检查**：按事件名 → 属性名 → 显示名 → 类型 → 枚举 → 对象结构的顺序查重，并把待确认项列出。
7. **交付三张表**：事件表、公共事件属性表、用户属性表；父属性和对象子属性都要有行。
8. **交研发和制作人审阅**：程序实现前确认命名权，程序自行改动时回传数据组；随后按项目验收流程执行。

## 禁止的捷径

- 不把通用行业埋点模板直接套到项目。
- 不把版本号或赛季名塞进事件名来代替版本字段。
- 不因为“以后可能分析”就把临时行为全部做成用户属性。
- 不把截图、表格渲染结果或“有多少行”当成方案知识。
