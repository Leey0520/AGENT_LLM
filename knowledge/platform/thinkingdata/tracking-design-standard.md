# 公司埋点设计标准

## 先解决什么问题

埋点是为了回答上线后的分析问题，不是把所有程序动作都记录下来。设计开始前必须读需求或版本内容，写清楚要判断的流程、状态变化、成功/失败/退出、奖励与网络边界，以及上线后要看的指标。

数数按事件上报个数收费。能用一个事件加 `action_type` 或 `step` 区分的同一流程，不要拆成大量重复事件；但粒度、属性集合或统计目的明显不同的事件必须拆开，例如 `enter_level` 和 `game_over`。

## 事件设计

- 先查当前方案，优先复用已有事件；冲突处理顺序是公司规则、最新方案、旧方案。
- 新事件使用英文小写 snake_case，通常按“模块_动作_对象”命名；不要以数字或 `#` 开头，不要把版本或赛季写入事件名，建议不超过 40 个字符。
- 事件名必须可读、互斥、体现触发逻辑，不能与历史事件重名。事件显示名使用稳定中文“动词+宾语”，同模块保持前缀，最好不超过 8 个字且不同事件不共用显示名。
- 单个事件的属性先描述一次行为的上下文；一个属性只表达一个维度，单事件属性通常控制在 30 个以内。
- 广告点击、播放成功、播放失败等结果不同的动作拆成独立事件；新手引导可以用一个事件配 `step`，不要为每一步建事件。

## 属性、公共属性和用户属性

- 先复用历史属性名、显示名、类型、枚举和对象结构；同一语义跨事件必须保持同名、同显示名、同类型。
- 公共事件属性只保留真正跨多个事件使用的会话上下文，至少有约 5 个事件复用时再提升为公共属性；只服务一个或少数事件的字段留在事件专属属性中。
- 用户属性用于长期稳定状态，例如拥有内容、余额、累计数和关键时间；临时行为、历史切片和单次事件上下文不要只放用户属性。用户属性接近 100 个时要重新评估是否必要。
- 枚举字段必须给出稳定英文值和中文映射；数值字段必须定义合理范围、单位和精度；文本、列表以及对象/对象组内的文本和列表也要给出 ID 或枚举说明。
- 输出固定为事件表、公共事件属性表、用户属性表。每个事件属性一行；对象/对象组父属性和每个子属性都要单独列出；不确定项标注“待确认/待补充/待人工确认”。

## 接入与发布硬规则

- 正式包和线上包必须使用 Normal 模式，不能使用 Debug 或 debug-only；Debug 只用于已配置 Debug 设备的测试包。
- 必须打开 ThinkingData 预置属性；`ta_app_start` 与 `ta_app_end` 都要开启，否则冷启动时长会异常。
- `EnableAutoTrack()` 只能调用一次并在一次调用中组合需要的自动采集类型，多次调用会覆盖前一次配置。
- 事件名、属性名的命名权要在程序和数据组之间提前确认。程序自行新增或修改埋点，必须在埋点群同步数据组。
- 客户端和服务端的 `#distinct_id` 必须能绑定到同一用户主体；不一致会生成两个用户。

## 交付前检查

读需求 → 明确分析目标 → 拆链路 → 查历史 → 设计事件 → 设计属性 → 判断公共/用户属性 → 处理对象结构 → 做冲突检查 → 输出三张表 → 标待确认项 → 交研发实现和测试。
