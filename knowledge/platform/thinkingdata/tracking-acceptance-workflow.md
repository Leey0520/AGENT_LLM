# 公司埋点验收流程

## 验收节奏

### 未上线版本

1. 测试组打包前：按测试用例触发全部待验收内容。
2. 测试组打包后：使用同一测试用例再次触发并确认修复项。
3. 上线当天：数据组早、中两轮验收所有渠道的核心数据（启动、进入游戏、注册、登录、付费等），下午第三轮验收全部埋点；三轮都补查“埋点管理 → 实时数据”，防止短时间重复上报或持续单条上报造成数据量异常。

### 已上线迭代版本

测试组仍按打包前、打包后两轮执行；上线当天数据组至少做一轮所有渠道核心数据验收，并按问题修复结果复测。

## 测试组在数数后台的操作

1. 进入“数据 → 埋点管理 → 数据验收”，时间范围覆盖当天测试时间；可选择全事件或指定事件。
2. 若事件分析尚未入库，先到“实时数据”查原始上报，不要立即判断为未触发。
3. 用“分析 → 事件分析”选择启动游戏、进入游戏等基数较大的元事件，筛选待验收版本和测试账号的账号 ID、凉屋账号 ID 或设备号；需要分渠道时加入渠道分组，时区通常使用 UTC+8。
4. 点击触发用户数进入测试用户列表，再打开行为序列核对：事件是否出现、属性是否出现、属性值和类型是否正确、事件顺序是否合理。
5. 全选事件看顺序边界，例如启动应先于进入游戏，注册/登录顺序合理，进入关卡后才有结束事件；对客户端与服务端相邻事件检查时区是否一致。
6. 用户属性按测试用例用户表逐项核对；同时检查 `#account_id` 和 `#distinct_id` 是否符合项目方案。对象/对象组必须点开原始明细，核对每个子属性的类型和值。

## 数据组复核

测试组同步第一轮结果并修复后，数据组用事件分析复核公共属性枚举和新增属性枚举，再把两张证据截图放回测试用例。

异常标注规则：未上报用橙色填充和红字说明；空值、无值、异常值可以打勾但必须同样标出具体问题。发现问题立即在埋点群同步，修复后重新触发，直到问题闭环。

## 常见异常与排查顺序

- 事件没有出现：先查实时数据，再查埋点方案是否启用、事件名是否与表格完全一致，最后确认代码触发路径。
- 属性在方案中但无上报：先查事件专属属性，再查是否误放成公共属性或字段名不一致。
- 中文显示名不一致：在“数据管理 → 事件属性/用户属性”搜索英文名和相近中文名，不能只凭界面中文判断是不同字段。
- 类型不一致：按 [数据类型与用户身份规则](data-types-and-identity.md) 先修上报，再处理错误元数据。
- 量级不符合：比较测试内容量、事件次数和用户数，检查是否重复上报、漏报、某渠道缺包或触发条件未覆盖。
- 行为顺序异常：检查客户端/服务端时间戳、时区、缓存补发和场景切换。

## 上线汇报模板

```text
【版本】埋点验收汇总
验收范围：版本新增埋点 + 老核心埋点（新增、活跃、留存、付费）
验收结果：老核心数据是否正常；新增内容哪一项异常
异常数据解决：修复包/热更/继续跟进
```
